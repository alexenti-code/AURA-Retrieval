# ТЗ: MMI-демон (mmid) v1

**Статус:** техническое задание к следующему этапу. Стенд (Python, MMI/stand)
доказал цифры; демон — production-форма с целевыми p99.

## 1. Назначение

Долгоживущий процесс `mmid`, обслуживающий пластичную память Φ(t) между
репликами диалога. Ядро K (облачная модель или локальная) обращается к mmid
по локальному протоколу; mmid выполняет запись/чтение следов и снапшоты.

Требования-мотивировки (из стенда 27.08.2026):
- горячая запись ≤ 5 мс p99 (стенд: 12.5 мс p50 на Python+numpy);
- никаких «пробуждений интерпретатора»: процесс стартует один раз;
- стабильный p99 под параллельными диалогами (нет GIL, нет GC-пауз).

## 2. Язык и стек

- **Rust** (edition 2021), без рантайма поверх — tokio для сети не обязателен
  на первом этапе: синхронный пул потоков достаточно (нагрузка — мс-операции).
- Хранилище: mmap-файл MW1 (формат стенда), запись fp16, аккумулятор fp32.
- Математика: ручное ядро rank-1 (SIMD через `std::arch` / `matrixmultiply`),
  BLAS не обязателен. GPU не нужен — это принципиальное преимущество архитектуры.

## 3. Интерфейс (локальный)

- Транспорт: Unix domain socket; JSON-lines или длино-префиксованный бинарь.
- Команды:
  - `write {entity, key_basis, vec, meta{event_t, obs_t, version, status}}` → `{latency_us, shard}`
  - `read {entity, key_basis}` → `{vec, score}` (score — косинус, сигнал «знаю/не знаю»)
  - `snapshot` → `{ms, regions}`; авто-снапшот по dirty-таймеру (по умолчанию 30 с) и по требованию
  - `trace {entity}` → история версий (би-темпоральная таблица)
- Семантика записи: асинхронная реплика в ответе диалога не блокируется;
  mmid подтверждает приём до применения апдейта (вrace-безопасно, один writer на регион).

## 4. Требования к надёжности

- Crash-consistency: снапшот атомарной заменой файла (write-to-temp + rename),
  dirty-журнал не нужен, потеря хвоста ≤ интервала авто-снапшота — допустима
  и документируется (память опыта, не транзакционная СУБД).
- Метрики: Prometheus-эндпоинт (write/read latency histogram, dirty bytes, p99).
- Ограничение памяти: LRU-выгрузка холодных регионов по caps (по умолчанию резидентно ≤ 50% файла).

## 5. Приёмочные критерии

1. p99 горячей записи ≤ 5 мс на 32 регионах d=4096 (одиночный диалог).
2. 8 параллельных диалогов: p99 записи ≤ 15 мс, чтения ≤ 10 мс.
3. Перезапуск процесса: recall всех проб не изменяется (≥ стенда B6).
4. Снапшот 1 ГБ ≤ 400 мс без блокировки горячих операций дольше 5 мс.
5. Суточный soak-тест: без утечек RSS, p99 деградация ≤ 10%.

## 6. Вне рамок v1

Консолидация регионов, семантический роутинг на живых эмбеддингах,
встроенная форма интерфейса внутри трансформера (аксиома 8 MMI).
